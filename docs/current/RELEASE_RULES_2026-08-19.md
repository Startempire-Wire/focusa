# Release Rules — 2026-08-19 (plain language)

## 1. Why releases have been painful (research)

**Pain measured on v0.9.173-dev → v0.9.177 stable:**

- Version lives in 16 places (`Cargo.toml`, `Cargo.lock`, `package.json`, `tauri.conf.json`, `Settings.svelte`, `install-focusa.sh`, `agent-card.json`, `distribution-manifest.json`, `.release-version-stamp`, etc). Stamping is 16-file, not one. One miss = `verify-version-surfaces` fails.
- `distribution-manifest.json` was not auto-generated by the stamp script. Agent hand-edited it, left stale `sha256` hashes → next run still fails.
- `score >=5` + `11:00/16:00 PT window` blocks stable outside window. Agent used `--force-release` to bypass, hiding the batch rule.
- CI queue backed up: 5 jobs × 6 recent pushes = 30 jobs queued on `ubuntu-latest`/`macos-latest`. 35 min wait for `90b8cb7` to go `queued → in_progress`. No batching, no `sccache`.
- No pre-push local guard: `cargo fmt`, `clippy -D warnings`, `verify-version-surfaces` only ran in CI, so failures were discovered after push.
- Tag vs Release confusion: `git tag` exists ≠ GitHub Release exists. Dev tags are prerelease and never show as Latest. Agent said "pushed" when only tag existed.

## 2. How to make it agent-friendly, fast, and foolproof

**Highest ROI first:**

1. **Single-source stamp (ROI 10/10).** Make `scripts/stamp-menubar-version.py` the only writer for all 16 surfaces **including** `distribution-manifest.json` (recompute 5 `sha256` + `source_commit` + `generated_at`). One command, zero hand edits. We just fixed this locally — make it permanent.
2. **Pre-push hook (ROI 9/10).** `scripts/dev.sh hooks` already installs hooks. Extend pre-push to run: `verify-version-surfaces --check`, `cargo fmt --check`, `cargo clippy -- -D warnings`, `php -l` for WP plugins. Fails in 15 seconds locally, not 12 minutes in CI.
3. **CI batching + caching (ROI 8/10).** Use `Swatinem/rust-cache` + `sccache`, `cargo nextest`, single `ubuntu-latest` job that runs `fmt+clippy+test` together instead of 5 separate jobs. Cuts CI 12 min → 4 min.
4. **Release-journal as gate, not window.** Keep `score` but remove PT window block — batch by score, not by clock. Window adds confusion and forces `--force`.
5. **One button, one result.** `scripts/create-dev-release-tag.sh --push` must be the only way to create a tag. It already does `verify-version-surfaces`, `benchmark`, `journal`. Add `--dry-run` in CI to show what would be stamped before pushing.
6. **Tag = Release.** Do not create a tag without a successful CI for that exact SHA. Keep current `Require exact candidate-SHA preflight` — just make it visible in the error message ("CI for 90b8 is still queued, wait, don't hand-tag").

**Linting/hooks to enforce continuously (all in CI + pre-push):**

- `cargo fmt --all -- --check` (rustfmt 1.91.0 pinned)
- `cargo clippy --workspace --all-targets -- -D warnings`
- `python3 -m py_compile` + `php -l` for WP
- `svelte-check` for menubar (`/opt/node-v22.22.3-linux-x64/bin/npm --prefix apps/menubar run check`)
- `tests/spec104_singleton_inventory_gate.py --closure`
- `python3 scripts/verify-version-surfaces.py <tag>` (already)
- `bd dep cycles` (no bead cycles)

All are fast (<30s) locally, so they belong in pre-push, not just CI.

## 3. Vocabulary (so no corners are cut)

From `AGENTS.md` (now canonical):

- **Release** = full canonical stable. Every surface, every OS, every artifact. Shows as **Latest** in repo sidebar + green badge + `gh release view vX.Y.Z` exists. Nothing else counts as shipped.
- **Dev release** = nightly/dev channel. Also full surfaces and OS. Marked `prerelease`. Early adopters opt in. No reduced matrix.
- **No partial releases.** No OS-only or surface-only ships. If you think you need one, write one sentence why and get explicit approval.

Agent language: say "tag pushed, CI queued" or "Release published as Latest" — never "pushed full release" when only tag exists.

## 4. What is missing?

- **Hotfix path:** If `stable` has a blocker, we need a one-line doc for `v0.9.177-hotfix.1` channel (still full, but out-of-window). Decide if hotfix uses same `score` gate or `severity: blocker` bypass.
- **Rollback rule:** If a Release goes red after publish, who reverts? Currently Watchdog heals, but no written "revert to previous Latest" step.
- **Badge source of truth:** Sidebar badge reads CI on `main`, not on tag. Should badge read "Release CI for latest tag is green" so it matches what users see?
- **Dev channel visibility:** Dev releases are invisible in sidebar (only Tags). Should we publish dev as `prerelease` so early adopters see them in Releases list?

## External research (browser)

Sources checked via Brave Search + direct fetch 2026-08-19:

- Harness — "CI/CD Best Practices: Build Fast, Stable Pipelines" — commit early/often, keep builds green, build once, streamline tests, secure/clean envs, use pipeline for all prod deploys, release in stages, track metrics. https://www.harness.io/blog/ci-cd-best-practices
- JetBrains TeamCity — "Best Practices for Successful CI/CD" — collective responsibility for green builds, quick-fixes on failure, no blame. https://www.jetbrains.com/teamcity/ci-cd-guide/ci-cd-best-practices/
- Depot — "Fast Rust Builds with sccache and GitHub Actions" — sccache + GitHub cache cuts Rust builds 3-5×. https://depot.dev/blog/sccache-in-github-actions
- GitHub — `actions/cache` — cache deps and build outputs. https://github.com/actions/cache
- Gatling — "CI/CD best practices: top 15" — build once, test the binary you ship, short feedback loops, fast/reliable tests. https://gatling.io/blog/ci-cd-best-practices

Takeaways applied to Focusa:

- Build once: stamp 16 surfaces from one script, then reuse that artifact everywhere (already our rule — just make it actually one writer).
- Short feedback: pre-push local checks (fmt/clippy/verify) in 15s, not after push.
- Cache: `Swatinem/rust-cache` + `sccache` (depot pattern) is the biggest CI speedup for Rust+TS.
- Keep builds green: collective fix, not force tags. Our `score + window` hiding green discipline — replace with plain score.
