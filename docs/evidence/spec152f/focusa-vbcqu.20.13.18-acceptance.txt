Bounded result
- Added the Spec 152E order-completion binding service. bindOrderComplete accepts
  only complete, eligible orders whose canonical EDD rows carry the exact account,
  registration, order item, price, and product binding, plus a real order-linked
  payment transaction. The canonical order row (status complete, customer_id exact,
  verified email digest) is authoritative: a 'complete' event for a canonical
  pending order fails EDD_ORDER_PENDING, for a canonical refunded order fails
  REFUNDED, and settlement follows canonical truth once the row is complete.
- One eligible protected order item settles exactly one entitlement issuance request:
  the service inserts one binding row (ob_ opaque token, state
  settled_pending_issuance) plus one issuance request row (ir_ opaque token, state
  pending, deferred to the verified issuance service) per (registration, order,
  order item). Duplicate completion events return the existing settlement
  (existing=true) and never create a second issuance request; idempotency-key
  replays return the identical decision; reusing a key for a different request fails
  IDEMPOTENCY_CONFLICT. The service never creates an EDD license, key, or lease
  (licenses_created 0).
- Synthetic/unlinked payment IDs fail closed with EDD_ORDER_UNVERIFIED and never
  issue: focusa_live_* and synthetic_*/manual/none markers, missing transactions,
  non-complete payment status, and transactions not bound to the exact canonical
  order are all rejected; matched payments are journaled only as keyed digests.
- Out-of-order fixtures: canonical-pending completion (denied, then settles after
  the row completes), canonical-refunded completion (denied, zero issuance, durable
  blocked binding journaled), and a terminal refunded event journaled before
  completion (later complete event returns decision out_of_order with
  entitlement_allowed false and zero issuance; repeated refunded events stay denied
  with no second blocked binding).
- Precondition failures fail closed with existing stable codes: unknown/unverified/
  denied registrations -> EMAIL_VERIFICATION_REQUIRED, verified-but-unpromoted ->
  EDD_CUSTOMER_RESOLUTION_FAILED, expired -> REGISTRATION_EXPIRED, wrong facade/
  origin -> FACADE_ORIGIN_DENIED, facade product allowlist and registration-vs-offer
  product mismatches -> FACADE_PRODUCT_DENIED, unknown download/wrong price ->
  PRODUCT_MAPPING_REQUIRED, frozen registry (no operator-approved download mapping)
  -> PRODUCT_MAPPING_REQUIRED, approved-but-blocked mapping -> EDD_CHECKOUT_REQUIRED,
  order customer/account mismatch -> ACCOUNT_MERGE_REVIEW_REQUIRED, changed
  canonical email -> ACCOUNT_EMAIL_MISMATCH, blank email/missing order row/order
  customer mismatch/missing item row/cross-order item -> EDD_ORDER_UNVERIFIED,
  existing active equivalent license -> EDD_LICENSE_UNUSABLE, pending/processing ->
  EDD_ORDER_PENDING, revoked -> REVOKED, caller-controlled commerce fields ->
  CLIENT_COMMERCIAL_FIELDS_FORBIDDEN. Unrelated/quarantined and credit-pack orders
  complete as no_entitlement with zero issuance.
- Journals store only keyed digests and opaque bounded tokens (ob_/ir_); no raw
  email, raw payment transaction id, secret, or unmasked real-email evidence appears
  in decisions or journals. Rollback is preservation-only (bindings and
  issuance-request journals are never deleted).
