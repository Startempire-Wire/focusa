Bounded result
- Added the Spec 152E branded EDD checkout intent contract. activation.checkout
  creates exactly one server-owned EDD checkout intent for a mailbox-verified,
  live, promoted (authority account + EDD customer bound) registration and returns
  a branded facade checkout URL. Unverified, expired, denied, and unpromoted
  registrations fail closed (EMAIL_VERIFICATION_REQUIRED, REGISTRATION_EXPIRED,
  EDD_CUSTOMER_RESOLUTION_FAILED); wrong facades/origins fail with
  FACADE_ORIGIN_DENIED and facade product-allowlist mismatches with
  FACADE_PRODUCT_DENIED.
- The product is resolved exclusively from the registration's product code through
  the server-owned registry: unknown codes fail PRODUCT_MAPPING_REQUIRED and
  offers that are not operator-approved/checkout-enabled fail EDD_CHECKOUT_REQUIRED.
  Caller-controlled price, amount, total, grants, features, limits, product,
  license-type, commercial, and EDD-id fields are impossible
  (CLIENT_COMMERCIAL_FIELDS_FORBIDDEN); caller-supplied callback/redirect/success/
  cancel/return URLs and arbitrary handles are never honored
  (FACADE_REDIRECT_DENIED).
- The branded facade URL is composed only of the facade's exact origin plus the
  allowlisted facade checkout path and an opaque intent token
  (https://install.focusa.dev/activate/checkout?intent=<opaque>); return handles
  are named facade-registry callbacks (success/cancel/recovery) resolved to branded
  callback URLs. Facades remain presenters only; no independent facade authority.
- Exactly one intent per promoted registration/product: an idempotency-key replay
  returns the same intent (replayed=true), a repeated canonical request with a new
  idempotency key returns the existing intent (existing=true) instead of creating a
  second one, and idempotency-key reuse with a different request fails
  IDEMPOTENCY_CONFLICT. The registration advances through the legal state machine
  path account_promoted -> offer_selected -> checkout_pending (the offer_selected
  hop journals independently via a derived key); an already-checkout_pending
  registration is not re-transitioned.
- Each intent binds registration, account UUID, EDD customer id, facade, product
  code, node request (node UUID plus device-public-key SHA-256 digest — the raw key
  is never stored), a server-owned cart session (synthetic fixture with the exact
  registry download/price relationship), the branded return URL, and the
  idempotency journal. No raw email, raw device key, license key, or secret is
  stored or returned; intent/cart rows are opaque bounded tokens.
- The EDD cart/session adapter projects the synthetic order fixture
  (focusa.spec152e.edd_order_fixture.v1) with order_id null, exact registry
  price_id/download and unit/total amounts, and no email. Zero EDD order/license
  rows are created: real order creation and issuance stay deferred to EDD payment
  and the order-completion atom.
