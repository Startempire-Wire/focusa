Bounded result
- Added the Spec 152E checkout identity-integrity handler. Protected EDD order
  completion locks the checkout email to the mailbox-verified registration
  identity: the assessment requires a verified, live, promoted registration bound
  to the exact facade/product, an order customer/account that matches the
  registration's promoted customer/account, and an order email that matches the
  verified registration email digest. An order email that is an already
  mailbox-verified identity safely linked to the same authority account also
  proceeds (prior mailbox control, never payment). Matching assessments return
  email_integrity_passed with entitlement_allowed true and issuance deferred.
- Changed, blank, or conflicting checkout emails, and order customer/account
  mismatches, journal a bounded fulfillment hold (decision fulfillment_held,
  entitlement_allowed false, issuance held_until_email_verified) with an opaque
  hold key (fh_) and review handle (hr_). Stable public-safe codes only:
  changed -> ACCOUNT_EMAIL_MISMATCH, blank -> EDD_ORDER_UNVERIFIED, conflicting
  and account -> ACCOUNT_MERGE_REVIEW_REQUIRED. Zero EDD licenses, orders, keys,
  or leases are ever created by this surface, and payment success alone can never
  promote the new email: a hold persists across repeats and retries (repeat
  returns the existing hold), idempotency-key reuse with a different request fails
  IDEMPOTENCY_CONFLICT, and the same held order still blocks even after the new
  email becomes verified until an explicit release review runs.
- Release requires a separately verified link review: the held email must be an
  existing mailbox-verified identity (primary/linked, verified_at set) of the
  exact same authority account, plus a bounded opaque review evidence handle.
  Evidence kind is fixed to 'verified_link_review'; payment/operator/facade
  evidence can never release a hold (payment_success -> EMAIL_VERIFICATION_REQUIRED).
  Release marks entitlement_allowed true (fulfillment_released) but issuance stays
  deferred to the verified issuance service; release replays are idempotent and a
  repeated canonical release returns the existing release.
- Precondition failures fail closed with existing stable codes: unknown/unverified/
  denied registrations -> EMAIL_VERIFICATION_REQUIRED, verified-unpromoted ->
  EDD_CUSTOMER_RESOLUTION_FAILED, expired -> REGISTRATION_EXPIRED, wrong facade ->
  FACADE_ORIGIN_DENIED, unknown download/wrong price -> PRODUCT_MAPPING_REQUIRED,
  blocked mapping/frozen registry -> EDD_CHECKOUT_REQUIRED (or
  PRODUCT_MAPPING_REQUIRED when the download is not assigned in the frozen
  registry), duplicate active license -> EDD_LICENSE_UNUSABLE, pending/refunded
  orders -> EDD_ORDER_PENDING/REFUNDED, caller-controlled commerce fields ->
  CLIENT_COMMERCIAL_FIELDS_FORBIDDEN. Unrelated/quarantined orders complete as
  no_entitlement with no identity requirement and no entitlement.
- Journals store only keyed digests (registration-secrets HMAC of the normalized
  email) and opaque bounded tokens; no raw email, secret, license key, or unmasked
  real-email evidence appears in decisions or journals. Rollback is
  preservation-only (holds and release journals are never deleted).
