# Spec 108 — Pi Plugin Awareness, Card, and Tool Communication Algorithm

Status: draft  
Owner: Verious Smith  
Created: 2026-06-15  
Parent work: `focusa-4jo5`  
Motivation: the Pi reload utility card remained stale and verbose after daemon utility-card work; operator clarified the target is not “shorter at any cost,” but the most useful, current, efficient awareness algorithm for a 70+ tool ecosystem.

## 1. Purpose

Define the algorithm used by the Focusa Pi plugin to decide what to show or inject across:

- auto-bootstrap / Pi reload card
- visible utility card
- system prompt awareness kernel
- post-compaction card
- Workpoint/Trajectory resume hints
- `focusa_*` tool descriptions and prompt snippets
- tool-family and next-tool guidance
- unsafe-root and scope-conflict recovery cards

The goal is **maximum decision usefulness per token**, not minimum tokens.

## 2. Core Principle

Verbosity is allowed when it carries decision value. Brevity is required when extra text repeats known state, stale assumptions, or low-actionability explanations.

The card/tool algorithm must preserve awareness of the Focusa ecosystem without dumping the ecosystem.

## 3. Problem

The current Pi plugin card renderer (`apps/pi-extension/src/awareness.ts::buildFocusaUtilityCard`) can emit long static sections:

- `MISSION_PACKET`
- `NOW_CARD`
- `WHY_CARD`
- `HEALTH_CARD`
- `DO_CARD`
- `RECONCILIATION_ENVELOPE`
- `Friendly Focusa Q`
- `Golden route`

These labels and prose can be useful in early onboarding, but became stale/noisy after newer surfaces (`focusa_utility_card`, WorkpointResumePacketV2, TrajectoryView, DX/UX digest, Context Cognition, tool choreography, project identity verification) became available.

The issue is not that the card is long. The issue is that it is not algorithmically selected from current state and tool affordances.

## 5. Output Classes

### 5.1 Awareness Kernel

Prompt-injected, compact, high-authority section for the model.

Required fields:

- project identity status
- authority boundary
- canonical Workpoint status
- Trajectory status/gap
- exact next action
- blocked/stale surfaces
- one recovery route

### 5.2 Visible Operator Card

Shown in chat when Pi reloads or scope is unsafe/stale.

Required fields:

- status line
- verified/bound project or unsafe-root warning
- exact next action
- why this matters
- what is intentionally not being done

### 5.3 Post-Compaction Card

Shown/injected after compaction/model switch/session resume.

Required fields:

- Workpoint resume status
- Trajectory north-star status
- current ask scope verdict
- evidence/proof handles
- exact continuation action
- do-not-drift list

### 5.4 Context-Pressure Warning

Shown only when context pressure or compaction risk changes enough to require operator/model awareness.

Required fields:

- context percentage/tier
- Workpoint anchor state
- exact action
- compaction/handoff behavior
- cadence state (first notice, escalation, repeated compaction)

Warnings must be transition-aware and deduped. Persistent pressure belongs in the status bar; visible warnings are for transitions/escalations.

### 5.5 Tool Description / Prompt Snippet

Each `focusa_*` tool should have:

- one-line purpose
- when to use
- output/decision value
- key guardrail if dangerous/stale-prone
- next-tool choreography

Descriptions must be current with tool behavior. They should not preserve old implementation history unless it affects use.

## 6. Dynamic Verbosity Algorithm

Every card is generated by scoring candidate lines, not by printing fixed prose blocks.

### 6.1 Inputs

- verified project identity
- project root safety
- continuity id
- canonical WorkpointResumePacket
- TrajectoryView summary
- current ask / operator steering
- active blockers / stale surfaces
- token/resource mode
- tool affordance graph and next-tools
- evidence refs and proof gaps
- recent prediction/metacog only when relevant

### 6.2 Line Scoring

Each candidate line gets a Decision Value Score (DVS):

```text
DVS = authority_value + actionability + risk_reduction + novelty + proof_value - redundancy_penalty - staleness_penalty
```

Definitions:

- `authority_value`: clarifies what can/cannot be trusted.
- `actionability`: tells the agent/operator what to do next.
- `risk_reduction`: prevents drift, unsafe writes, false closure, or scope mismatch.
- `novelty`: adds new state not already visible.
- `proof_value`: carries evidence refs or verification handles.
- `redundancy_penalty`: repeats already-injected context.
- `staleness_penalty`: uses fallback, old labels, or unverified assumptions.

### 6.3 Verbosity Modes

- `minimal`: only authority + next action + blocker.
- `standard`: adds why + evidence refs + recovery route.
- `rich`: adds tool-family map, proof gaps, and learning/prediction hooks.
- `onboarding`: includes glossary-like explanations and Friendly Q prompts.

Mode selection:

- unsafe root / scope conflict → `standard` with recovery, not onboarding dump.
- verified active Workpoint → `minimal` or `standard`.
- post-compaction → `standard`.
- operator asks for architecture/design → `rich`.
- first-ever project onboarding → `onboarding`, bounded and dismissible.

## 7. Tool Ecosystem Integration

Focusa has many tools; awareness must guide selection without listing all tools.

Required grouping:

- Project identity / scope
- Workpoint / continuation
- Trajectory / goal ladder
- Evidence / proof
- Context cognition / curation
- Tool contracts / choreography
- Prediction / metacog
- Diagnostics / DXUX / recovery
- Resource/LowMem
- Work-loop control
- UIAI/browser diagnostics

Each card may include at most:

- top 3 best next tools
- top 3 recovery tools
- one “do not use by default” list when risk exists

The full registry remains accessible via tool contracts and context cognition, not printed into every card.

## 8. Freshness Requirements

Pi plugin card/tool guidance must refresh when any of these change:

- new tool added/removed/renamed
- tool contract count changes
- Workpoint packet schema changes
- Trajectory/project identity authority changes
- DX/UX or utility-card fields change
- post-compaction/Focus Slice schema changes
- operator-facing public docs change core claims

A static audit must detect stale labels and mismatched tool counts.

## 9. Forbidden Failure Modes

- Printing unsafe `/root` as if it were a usable project root.
- Showing long onboarding copy after verified project scope exists.
- Treating transcript tail as authority.
- Listing 70+ tools in a bootstrap card.
- Hiding exact next action behind general philosophy.
- Claiming completion from partial/surrogate evidence.
- Keeping stale terms such as `MISSION_PACKET` if the current algorithm uses a different schema.
- Repeating context-pressure/compaction warnings every turn while state has not changed.

## 10. Acceptance Criteria

Spec108 implementation is accepted when:

1. Pi reload visible card is generated from the dynamic algorithm, not a fixed stale prose block.
2. System prompt awareness kernel is compact but includes authority, next action, blocker, and recovery.
3. Post-compaction card uses WorkpointResumePacket + Trajectory + current ask scope, not transcript tail.
4. Unsafe-root card tells the exact project identity verification action and remains short.
5. Verified-project card does not show `UNBOUND_UNSAFE_ROOT` or onboarding Q-list.
6. `focusa_*` tool descriptions/prompt snippets are audited for current behavior and concise decision value.
7. Static test fails if stale labels (`MISSION_PACKET`, `NOW_CARD`, `WHY_CARD`, `HEALTH_CARD`, `DO_CARD`, `RECONCILIATION_ENVELOPE`, `Friendly Focusa Q`) reappear in default reload output.
8. Static test proves tool count/contract count/card tool-family count stay synchronized.
9. Runtime or renderer test proves `/root` unsafe case and `/home/wirebot/focusa` verified case produce distinct, correct cards.
10. Context-pressure warning test proves hard/handoff warnings dedupe and escalate only on state/risk change.
11. Jiti/runtime cache refresh or reload proof shows Pi uses the new source.
